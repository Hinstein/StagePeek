# 场馆演出座位图自动化工作流

## 结论

当前项目已经具备“按场馆同步演出候选和公开座位图引用”的自动化链路，但还没有、也不应该宣称已经实现“任意场馆、任意演出完全无人值守地生成可信 3D 舞台模型”。

票务系统通常能提供事件、日期、场馆和公开座位图引用；它通常不会提供可直接用于 SeatPeep 的舞台 CAD、逐座三维坐标、封闭看台规则、延伸台尺寸或真实比例。因此自动化的正确终点是：自动抓取候选，自动生成草稿，自动校验几何，只有来源匹配通过后才发布布局。

## 当前已经实现

1. `scripts/ticketmaster-sync.mjs` 按场馆调用 Ticketmaster Discovery API，读取事件元数据和 `seatmap.staticUrl`，写入 `data/ticketing/ticketmaster-events.json`。
2. API key 只在服务端使用。前端只看到规范化后的事件和公开引用，不会看到密钥，也不会把实时库存伪装成永久座位数据。
3. `GET /api/venues/:id/events` 合并场馆官方事件缓存和票务候选。候选默认标记为 `layout.status=unconfirmed`、`stageVerification=unverified`。
4. 已经核验的演出可在 `server/events.mjs` 中提供事件级布局，2D 和 3D 共用同一坐标系；事件布局不会污染永久场馆壳体。
5. `scripts/audit-scenes.mjs` 批量检查所有目录场馆的有限坐标、座位与舞台碰撞、看台表面与舞台碰撞以及布局组合。最近一次检查覆盖 197 个场馆、582 个布局组合，几何失败数为 0。

## 一次同步的实际流程

```text
场馆身份
  -> 票务事件候选
  -> 事件级公开座位图引用
  -> 图像/SVG/结构化数据草稿
  -> 舞台与封区草稿
  -> 独立来源校验
  -> 几何校验
  -> 浏览器验收
  -> 发布一个不可变布局版本
```

运行示例：

```bash
TICKETMASTER_API_KEY=... npm run ticketing:sync -- --venue sofi
node scripts/audit-scenes.mjs docs/audits/scenes-2026-10-25.json
```

同步只会生成候选，不会自动把候选提升为准确舞台。这样可以防止场馆名称相似、中文名称归一化为空、旧座位图或临时演出布局被误写入正式几何。

## 每一级如何验证

### 1. 场馆身份验证

- 优先使用供应商 `venueId`，其次使用名称、城市、国家和地址的组合。
- 名称不能单独作为唯一条件。特别是中文名称在 ASCII 归一化后可能为空，必须拒绝空字符串匹配。
- 供应商返回的城市和国家必须与目录一致；不一致的结果进入人工复核。
- 事件应保存供应商事件 ID、来源 URL、抓取时间和响应版本。

### 2. 事件和座位图验证

- 事件名称、日期、场馆和官方票务 URL 要相互一致。
- 座位图只记录为公开参考，保存 URL、抓取时间和内容哈希；不把图片直接当作逐座坐标。
- 如果事件没有公开座位图，状态保持 `unavailable`，不能用通用舞台替代并标成已确认。
- 事件更换座位图时生成新版本，旧版本保留以便回滚。

### 3. 布局提取验证

提取顺序应是：官方 SVG/JSON 或供应商结构化数据，之后才是公开图片描摹，最后才是参数化估算。每个字段都单独记录来源和置信度：

- 场馆轮廓和楼层：永久场馆来源；
- 事件座位块、封区和舞台：事件来源；
- 逐座 ID/坐标：只有确有来源时才标为 source；
- 行列、米制和高度：没有实测或图纸时标为 estimated；
- 舞台、延伸台、屏幕、FOH：必须是事件级对象，不能从永久场馆默认值继承后假装准确。

### 4. 独立证据校验

几何自检只能证明模型内部没有明显错误，不能证明它符合真实演出。发布前至少做以下独立检查：

- 原始座位图与生成的 2D 图叠加，检查舞台方向、分区数量、缺口、封闭看台和内场边界；
- 用未参与拟合的分区编号、分区间隙和外轮廓做 holdout 检查；
- 检查票图中明显的舞台主台、延伸台、侧台和 FOH 是否都出现在模型中；
- 有可用实测距离时，用未参与缩放的距离点复核比例；没有实测数据时明确显示“估算”；
- 反向校验：从模型点击分区和座位，必须能回到同一来源编号或明确的模拟编号。

### 5. 几何和浏览器校验

- 所有坐标必须有限，所有多边形闭合且不自交；
- 座位不能穿过舞台、看台表面、屏幕或设备区；
- 看台的行带不能跨越来源图中的通道或缺口；
- 2D 和 3D 使用同一布局坐标，切换视图不能改变选中的分区或座位；
- 逐场截图检查总览、2D、座位入座和移动端手势；
- 清缓存重新打开、切换场馆、切换演出和深链接都要验证，避免只验证当前内存状态。

## 发布状态机

布局必须按以下状态流转：

```text
candidate
  -> source-matched
  -> geometry-checked
  -> reviewed
  -> preview-published
```

任何一步失败都保留候选和失败原因，不得自动提升。正式页面只使用 `reviewed` 或 `preview-published` 版本；无法证明舞台来源的演出继续显示“布局待核实”。

## 目前仍需补的自动化

- 用稳定的供应商场馆 ID 和地址做匹配，修复中文名称为空导致的宽松匹配；
- 分页读取事件，不能只取单页 50 条；
- 加入公开座位图抓取、哈希和版本变更检测；
- 增加 SVG/JSON 优先的布局提取器和图片描摹草稿，不直接发布草稿；
- 增加来源图叠加、holdout 锚点、舞台方向和比例校验；
- 把候选审核和布局提升做成管理员操作，并保留回滚版本；
- 对每个被发布的事件自动生成 2D/3D/座位入座截图和审计记录。

因此，当前可以自动完成“发现和入库”，也可以自动完成“模型内部质量检查”；“真实舞台是否摆对”仍由来源匹配和审核门槛决定。对欧美 MVP，这个边界是必要的，否则会出现接口成功、测试全绿，但舞台仍然挤到座位里的情况。
